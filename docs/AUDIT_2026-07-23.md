# Agent Nudge Product and Repository Audit

Date: 2026-07-23

## Executive finding

Agent Nudge is a credible engineering prototype with a weak adoption path. The repository contains a local daemon, SQLite ledger, CLI, MCP server, Electron dashboard, Windows packaging, deterministic routing, context packs, path claims, receipts, and reversible connectors for Claude Code, Codex, and OpenCode.

The public product previously presented these capabilities as a single landing page plus an in-memory dashboard simulation. A visitor could understand the idea but could not move cleanly through discovery, trust, installation, connection, first proof, and repeated use.

## What is strong

- Specific problem: stale decisions, edit collisions, and repeated failed approaches across coding agents.
- Clear protocol: declare, preflight, act, receipt.
- Deterministic and inspectable relevance factors.
- Local-first storage and deliberate transcript avoidance.
- Reversible, dry-run-first provider connectors.
- Windows installer and portable build process.
- Meaningful unit, integration, end-to-end, connector, rollback, privacy, and release smoke evidence.
- Honest capability language around covered and uncovered provider actions.

## Principal risks

### P0: multiple database writers

Electron opens SQLite before determining whether a compatible standalone daemon already owns the local port. The daemon must become the sole writer and every other surface must communicate through the authenticated local control plane or durable outbox.

### P0: unauthenticated loopback API

Loopback binding prevents ordinary remote-network access but does not authenticate local clients or prevent service impersonation. Add a per-installation secret or stronger operating-system IPC identity, Host and Origin validation, secure token storage, rotation, and an authenticated health challenge.

### P0: non-transactional multi-record operations

Check-in, claim creation, fact fan-out, acknowledgement, release, and connector operations span multiple writes without a complete transaction and recovery model. Crash recovery must become deterministic.

### P0: active path claim race

Claim uniqueness is currently checked in application code. Enforce one active claim per project and normalised path at database level.

### P1: outcome metrics overclaim

Delivery and acknowledgement are not proof that a conflict was prevented. Separate detection, delivery, review, acknowledgement, action change, release, prevention evidence, false positive, and bypass.

### P1: dashboard protocol divergence

The dashboard acknowledgement path must use the ownership-checked versioned endpoint. Other feedback mutations need the same project, recipient, state-transition, and receipt guarantees.

### P1: demo contamination

Desktop proofs create timestamped sessions and claims in the normal project ledger. Use a temporary namespace or ledger with automatic cleanup.

### P1: source confidence language

Evidence attached plus author-provided confidence is not equivalent to independent verification. Introduce explicit provenance levels.

## Release order

### v0.5: reliability, trust, and adoption

1. Sole-writer daemon and canonical data path.
2. Transactions, uniqueness, operation journal, and crash recovery.
3. Authenticated local control plane.
4. Unified versioned feedback and receipt semantics.
5. Correct metrics.
6. Isolated first-run proof.
7. Published Windows release assets with checksums and explicit signature status.
8. Guided onboarding and Shadow Mode foundation.

### v0.6: evaluation and provider coverage

1. Shadow Mode evaluation report.
2. Nudge Replay Lab.
3. Worktree and branch awareness.
4. Provider conformance suite.
5. GitHub Copilot, Cursor, and Gemini connector research and selected implementations.
6. Provenance ladder and context-poisoning controls.

### v0.7: controlled team coordination

1. Encrypted team sync.
2. Signed context packs.
3. Shared policy and audit exports.
4. Role-based administration and retention controls.
5. Controlled remote-agent bridge.

Cloud sync must not precede the v0.5 reliability boundary.
